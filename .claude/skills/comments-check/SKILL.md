# 代码注释质量检查

对代码进行三维注释审查：**覆盖度** → **准确性** → **小白可读性**。

## 用户参数

`$ARGUMENTS` 是用户指定的检查范围：
- **不填**：检查 `src/` 和 `server/` 下所有 `.ts` 和 `.tsx` 文件
- **填文件名**：只检查那个文件，如 `src/api/index.ts`
- **填目录**：检查整个目录，如 `server/`

---

## 第一步：扫描目标文件

用 Glob 找到所有要检查的文件，跳过：
- `node_modules/`、`dist/`
- `.test.ts`、`.test.tsx`（测试文件）
- `.d.ts`（类型声明文件）

---

## 第二步：三维审查

### 维度一：注释覆盖度

**标准**：每 10 行代码中，至少 3 行是注释（30% 比例）。

**检查项**：

| 检查点 | 标准 | 评分 |
|--------|------|------|
| 文件头注释 | 文件开头应有说明：这个文件是干什么的 | 必须 |
| 函数注释 | 每个 `export function` / `export async function` 前应有 JSDoc 或行注释说明用途、参数含义、返回值 | 必须 |
| 核心逻辑注释 | 复杂计算、条件判断、数据处理流程应有注释解释"为什么这么做" | 必须 |
| 组件注释 | 每个 React 组件应有注释说明它的作用和 props 含义 | 必须 |
| 类型/接口注释 | `interface` 和 `type` 的每个字段应有注释说明含义 | 建议 |
| 注释率 | 整体注释行数 ÷ 总行数 ≥ 30% | 必须 |

### 维度二：注释准确性

**标准**：注释描述的内容和代码实际做的事情一致。

**检查项**：

| 检查点 | 怎么判断 |
|--------|---------|
| 功能匹配 | 注释说"获取用户列表"，代码是否真的是获取用户列表？ |
| 参数匹配 | 注释说参数是 `id`，代码里用的变量是不是 `id`？ |
| 逻辑匹配 | 注释说"金额为正时才计算"，代码是否真的判断了 `> 0`？ |
| 过时注释 | 注释说返回 3 个字段，代码实际返回了 5 个？ |
| 错误描述 | 注释写"找不到时返回 null"，代码是否真的返回 null？ |

### 维度三：小白可读性

**标准**：注释用通俗语言写，零基础的人能看懂。

**检查项**：

| 检查点 | ❌ 不好 | ✅ 好 |
|--------|--------|------|
| 避免术语 | "用 LRU 算法做缓存淘汰" | "缓存满了就删掉最久没用的" |
| 解释缩写 | "用 JWT 做 auth" | "用 JWT（一种登录凭证，像一张电子身份证）来验证用户身份" |
| 说明为什么 | `count++ // 加 1` | `count++ // 统计有多少条记录` |
| 参数解释 | `// id: number` | `// id: 账单的唯一编号，比如 5` |
| 生活化比喻 | "异步并发请求" | "同时发多个请求，不用排队等" |

## 第三步：输出审查报告

按以下格式输出：

```
📋 注释质量审查报告

┌─────────────────────────────────────────────┐
│  📊 总览                                    │
│  检查文件：X 个                              │
│  ⭐ 总评分：XX / 100 分                     │
│  维度一（覆盖度）：XX / 40 分               │
│  维度二（准确性）：XX / 30 分               │
│  维度三（可读性）：XX / 30 分               │
└─────────────────────────────────────────────┘

🔴 严重问题（必须修复）：
  • [文件:行号] 问题描述 → 修复建议

🟡 建议改进：
  • [文件:行号] 问题描述 → 改进建议

🟢 做得好的地方：
  • [文件:行号] 好的注释示例
```

**评分规则**：

| 维度 | 满分 | 扣分规则 |
|------|------|---------|
| 覆盖度 | 40 | 每个缺少注释的函数/核心逻辑扣 5 分 |
| 准确性 | 30 | 每个不匹配的注释扣 10 分 |
| 可读性 | 30 | 每个术语/缩写未解释扣 5 分 |

---

## 修复模式

如果用户要求修复，按以下优先级处理：

1. **先修严重问题**：修复缺失注释、错误注释
2. **再改可读性**：把术语改成大白话
3. **最后补细节**：给 interface 字段加注释

---

## 注意事项

- 检查的是**注释质量**不是代码质量，不要顺便改代码
- 用中文写审查报告，用 Emoji 标记严重程度
- 对零基础用户要解释清楚每个发现的问题
- 提出的修复建议要具体可执行，不要泛泛而谈
